# Users

This project manages users for one local driving school. User accounts are Orchid users extended with local security status and optional staff profile records. The feature does not add tenants, SaaS accounts, platform owners, subscriptions, or multi-company isolation.

## User Statuses

User lifecycle state is stored in `user_statuses`.

Seeded statuses:

- `active` is the default status.
- `inactive` is available for local workflow separation.
- `blocked` marks an account as blocked.
- `archived` marks an account as archived and final.

Only one status can be default. The default status must remain active. Blocking or archiving a user status makes the user lockout helper return true, and the last Superadmin cannot be moved into a blocked or archived status.

Allowed transitions:

- active can move to inactive, blocked, or archived
- inactive can move to active, blocked, or archived
- blocked can move to active or archived
- archived is final unless the explicit override permission is used

The lifecycle actions protect the last active Superadmin and prevent a current user from blocking or archiving their own active access by accident.

Run the status seeder after migrating:

```bash
php artisan db:seed --class=UserStatusSeeder
```

## Staff Profiles

Staff profiles are stored in `staff_profiles` and are one-to-one with `users`.

They hold local employee data:

- staff number
- branch
- translated display name, job title, and public bio
- phone and work email
- preferred locale and timezone
- avatar path
- public website visibility flag
- internal notes
- creator and updater references

Staff numbers generated by the security action use the format `STAFF-2026-0001`. The demo seeder uses factories and can be safely rerun:

```bash
php artisan db:seed --class=StaffProfileDemoSeeder
```

## Account Lifecycle Actions

The backend user management layer now supports internal staff user creation, safe updates, blocking, unblocking, archiving, status changes, profile preference updates, forced password-change flags, seen tracking, display-name resolution, login eligibility checks, access revocation on block, staff profile creation, and security summaries.

Create and update actions can sync roles and branch access when those payloads are provided. Profile actions deliberately do not change roles, permissions, statuses, or branch access.

Blocking and archiving revoke tracked active sessions when security-session tracking is available. The account is not physically deleted by default.

Audit records are written for user creation, updates, blocks, unblocks, archives, status changes, profile changes, forced password-change changes, and session revocation. Security events are written for block, unblock, archive, high-risk role assignment, and forced password-change events. These integrations are fail-safe.

The login check result is structured:

- `allowed`
- `reason`
- `status_code`

Known reasons are allowed, inactive, blocked, archived, must-change-password, and unknown.

## Validation

User status and staff profile writes have dedicated Form Requests, custom validation rules, and translated error messages. Locale values must match active project languages, timezones must be valid PHP timezones, staff numbers must match the project format, and each user can have only one staff profile.

## Login And Session Evidence

User accounts expose login attempts and active security sessions through relationships. Session records store only hashed session identifiers, and revocation actions protect the current Superadmin from accidental lockout. Laravel and Orchid authentication remain unchanged.

## Limitations

Dedicated user lifecycle screens are still a later step. This step adds the backend actions, requests, rules, translations, permissions, documentation, factories, and tests that those screens will call.
